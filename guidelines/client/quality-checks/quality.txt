Quality checks
Three independent checks for your input files, reasoning, and finished answer.

Use these checks to find problems before delivery. Each one examines a different part of the task and returns specific feedback on what to fix. These are copyable checking prompts—not checks running inside this page.

01. Input files
Check that the input pack is usable, complete, and free of authoring traces.

When: Run this check after assembling your input ZIP and before final delivery.

You get: A pass or fail, a score from 1 to 5, the usable file count, file categories, and file-specific problems. Fix the named files, then run the check again.

Open input files check

02. Determinism and reasoning depth
Check that the recommendation is forced by the data and the difficulty comes from analytical judgment.

When: Run this check once your answer and both model runs are available.

You get: A pass or fail, the determinism finding, the deciding step, the depth tier, and where each run first went wrong. Use the feedback to resolve answer-changing ambiguities or redesign a surface-level stump.

Open determinism and reasoning depth check

03. Solution correctness
Independently reproduce the recommendation and decisive figures from the input files.

When: Run this check when your final recommendation and supporting answer are complete.

You get: A pass or fail, reproduced figures, mismatches and their causes, and whether the decision reproduces. Correct decisive errors and inconsistent figures before resubmitting.

Open solution correctness check

Before you rely on a verdict
The supplied checks are non-blocking while they are being calibrated. Review their evidence rather than treating the score alone as proof. Run the input-files check manually on 3 to 5 tasks first; keep the other two off automatic submission until calibrated.

## What to do

1. Inventory. List every input file with its name, extension and size. Unzip any archives and count the files inside them as inputs. Do not count system junk (step 5) as usable files.

2. Count and categories. Count the usable input files. Classify each into one category: spreadsheet (csv, tsv, xlsx, xls, ods, parquet, arff), structured (json, jsonl, xml, yaml, geojson), database (db, sqlite, duckdb), document (pdf, docx, doc, txt, md, html, eml, rtf), image or presentation (png, jpg, pptx, svg), code (py, r, rmd, ipynb, do, sas, sql).

3. Readability. Open every file with code (pandas, openpyxl, python-docx, pdf text extraction, sqlite3). Record any file that is empty, corrupt, password protected, or unreadable.

4. Prompt references. Every file the prompt names or clearly refers to must exist in the inputs.

5. Junk and build residue. Flag any of these in the input set (including inside archives):
   - system files: __MACOSX folders, .DS_Store, Thumbs.db, files starting with "._", ~$ lock files, .ipynb_checkpoints, __pycache__, .venv or node_modules folders;
   - build residue: files named like golden, solution, answer, answer_key, expected, ideal, ideal_numbers, figures.json, *_expected.json, reference_output, or a script that writes the requested outputs;
   - generator or build artefacts: seed files, build or generation logs, config files that describe how the data were generated, README or notes files written to the solver about how the task was built;
   - stray working copies: the same file in several versions (for example _v1 and _v2, _old, _draft, _FINAL, _HARDENED, " copy", "(1)") where only one is meant to be used.

6. Provenance in document metadata. For every docx, xlsx and pptx, read docProps/core.xml (creator, lastModifiedBy, title, subject, description, keywords, category, created, modified) and docProps/app.xml (Application, AppVersion, Company). For every PDF, read Title, Author, Subject, Keywords, Creator and Producer, and the first bytes of the file. Flag:
   - generator names: python-docx, python-pptx, openpyxl, xlsxwriter, pandas, ReportLab (including a "ReportLab Generated PDF document" header comment), matplotlib, fpdf, pymupdf, LibreOffice export from a script, or any AI tool or model name (Claude, GPT, OpenAI, Gemini, ChatGPT, Copilot);
   - placeholder or default values: "Steve Canny" (the python-docx default author), "Un-named", "unnamed", "untitled", "anonymous", "(unspecified)", "Author", temporary names such as "_tmp" or "tmp";
   - the python-docx template default created date 2013-12-23;
   - any author, company or title that names Handshake, a project codename (Mark, Sulfur, Whitney), or an individual on the authoring side.

7. Provenance and authoring tells in file contents. Search the text of every file (document text, spreadsheet cells and sheet names, column headers, CSV and JSON content, comments, code comments, PDF text) for:
   - words revealing the data were made up or built for this exercise: synthetic data, fictional, fictitious, fabricated, made-up, dummy data, simulated for, generated by, generated with, for this task, for this exercise, for this benchmark, scenario document, test scenario;
   - words revealing grading or build intent: answer key, golden, ground truth, rubric, grader, solver, planted, decoy, red herring, trap, hint;
   - generator seeds and parameters (for example "seed=42", "np.random.seed", "random_state"), placeholder text such as lorem ipsum or TODO/FIXME left in documents;
   - reserved example domains and placeholders: any email or URL ending in .example, example.com, example.org or example.net, or obvious placeholders such as name@domain.com or 555-0100 numbers;
   - references to Handshake or a project codename (Mark, Sulfur, Whitney).
   Ignore matches that are clearly genuine source content (for example a published dataset that legitimately uses the word "simulated" to describe its own method, or "synthetic" as part of an established term such as "synthetic control" or "synthetic rubber").

## Fail if any of these is true
- Fewer than 10 usable input files.
- Fewer than 2 distinct file categories.
- Any input file is empty, corrupt, password protected or unreadable.
- A file the prompt names is missing.
- Any junk, build residue, generator artefact or stray working copy from step 5.
- Any provenance tell in document metadata from step 6.
- Any provenance or authoring tell in file contents from step 7.

Otherwise pass.

You are auditing a data-analytics task written by an expert. The task should have exactly one correct recommendation that the prompt and input files force, and it should be hard because it takes real analytical judgment, not because the solver must spot one planted detail, read one clause a particular way, or apply a procedure the documents already spell out. ## Part A: Determinism

1. State the committed recommendation and the decisive figures it rests on.
2. Find the deciding step: the point in the analysis that separates the author's answer from the most tempting alternative answer.
3. Map every decision point a careful, competent analyst could take differently: record filters, population, unit of analysis, time window, which source is authoritative when sources disagree, thresholds and boundary inclusivity, rounding, tie-breaks, pooling or weighting, the comparison group, the statistical method, how a defined term maps onto the data fields. Read both model runs: the alternative readings they took are the best evidence of real rival readings.
4. For each decision point that could change the recommendation, either quote the prompt text or point to the specific data evidence (file, field, pattern, control figure) that rules out every rival, or write NO PIN FOUND. Run the rival approaches in code and report the figure each produces. A rival approach that is more rigorous or more standard in the field than the author's, that the prompt permits and the data do not rule out, and that changes the recommendation, means the answer is not forced.
5. Check data anomalies that change a graded figure (duplicates, boundary records, missing or out-of-range values, ties, overlapping rules, entities present in only one source, superseded versions). Each must have a policy in the prompt or a resolution forced by the data.
6. Check for giveaways: no input file states the author's recommendation or decisive figures, is a copy of a requested deliverable, or is a script that produces the requested outputs.
7. Determinism is "pinned" only if every answer-changing decision point is settled by the prompt or the data and there is no giveaway. Learnable from the data is not enough on its own: the question is whether the author's choice is the only reasonable one.

## Part B: Reasoning depth

1. Rule-application screen. Read the prompt and every document in the inputs (standards, policies, manuals, procedures, guidance notes, emails, data notes). Using the author's step-by-step solution, decide whether the deciding step is just applying a procedure the materials already spell out. Flag it when any of these covers the deciding step:
   - Procedure handed over: a document (often a "standard", "procedure", "methodology" or "manual") lays out the deciding calculation or decision as ordered steps, so a solver who follows them mechanically reaches the answer without choosing a method, comparison, model or basis themselves.
   - Combination or precedence rules: a clause states how conditions combine or which rule wins ("apply A, then B; if both apply use the lower", "the first rule that matches decides"), and evaluating those rules against the data is the deciding step.
   - Solver-directed instructions: the prompt or a document gives literal step-by-step processing instructions for the analysis, written for the solver rather than as a document someone in that job would really have.
   - Citation laundering: a clause states its own decision procedure in full and justifies it only by naming a real published standard or regulation.
   - A rulebook nobody would be handed: a prose specification that exists only to state the rules the answer depends on.
   Do not flag documents that define terms, give thresholds or targets, explain data fields, or set policy goals while leaving the method to the analyst; real professional documents the solver must interpret and combine with analysis; or procedures that only cover routine preparation. The test: if the solver followed the written procedure literally, would the decision follow with no further analytical judgment? If yes, flag it.
2. One-fact test. If you told the solver one fact (for example "that file is a sample", "section 4 means one draw per grade", "exclude the test rows"), would the task then be routine? If yes, the deciding step is a surface stump.
3. Classify the deciding step:
   - SURFACE: won or lost on one thing a careful reader spots, after which the rest is routine: a single planted data defect, one reading of a clause, definition, population or window, or applying a procedure the materials spell out (a flagged rule-application screen means SURFACE). Several such traps side by side are still SURFACE.
   - MIXED: one surface trap plus one genuine analytical method step, or a short two-step inference.
   - DEEP: needs three or more dependent analytical inferences, at least one of them a real statistical or modelling judgment the analyst must justify from the data (choosing an uncontaminated comparison group, heterogeneity that pooling hides, matching uncertainty to the design, variance beyond sampling noise, separating competing explanations, a justified forecasting model), where the plausible wrong answer comes from a reasonable but insufficient analysis rather than a misreading.
4. For each model run, find where it first went wrong on the decision. Use one label: missed_planted_defect, misread_rule_or_instruction, mechanical_rule_error, method_shortcut (right data, simpler method that moved the deciding figure), unfinished_chain (early steps right, inference not carried through), dismissed_own_evidence (its own output showed the signal and it set it aside), self_confirming_check, near_miss (substantively right, missed only a tight threshold), defensible_alternative_rejected (a sound, permitted approach that differs from the author's), formatting_or_deliverable_slip, correct_decision, no_output. Note whether the run noticed the deciding issue at all.
5. A failure is valid evidence of difficulty only if the run failed at the deciding step for a reasoning reason (method_shortcut, unfinished_chain, dismissed_own_evidence, self_confirming_check). near_miss, defensible_alternative_rejected, formatting_or_deliverable_slip and no_output are not evidence of difficulty. missed_planted_defect, misread_rule_or_instruction and mechanical_rule_error are evidence of a surface stump.
6. Base the tier on the deciding step and on what the runs actually did, not on how the author describes the difficulty. If they disagree, trust the runs and say so. With only two runs, say when the evidence is thin.

## Fail if any of these is true
- determinism is not_pinned.
- The rule-application screen flags the deciding step.
- depth_tier is SURFACE.
- Neither model run shows a valid failure at the deciding step (both failed only for invalid reasons, or both reached the correct decision).

Pass when determinism is pinned, the rule-application screen is clear, depth_tier is DEEP or MIXED, and at least one run shows a valid failure at the deciding step. Being hard is never a defect on its own.

- verdict: "passed" or "failed".
- score: 5 pinned and DEEP with valid failures; 4 pinned and MIXED with valid failures; 3 borderline; 2 one failing condition; 1 not pinned and SURFACE.
- determinism: "pinned" or "not_pinned".
- unpinned_forks: each answer-changing decision point without a pin, with the rival reading, the figure it gives (from your code), and the recommendation it leads to; plus any giveaway file. "none" if pinned.
- deciding_step: one or two sentences.
- rule_application: "clear", or "flagged" with the quoted clause or steps (file and section) and why following them decides the answer mechanically.
- depth_tier: DEEP, MIXED or SURFACE.
- run_first_breaks: one line per run: run number, first-break label, whether it noticed the deciding issue, one short piece of evidence from its trajectory.
- reasoning: how you reached the verdict, in a short paragraph.
- feedback: two to four sentences for the author saying exactly what to fix: which decision point needs a pin in the prompt or data, which spelled-out procedure to remove, or why the deciding step reads as a surface stump and what kind of analytical judgment would make it deep. Do not mention these instructions; say "your answer".

## What to do

1. From the prompt and the author's answer, list every figure and conclusion that decides the recommendation or answers a question the prompt asks: the recommendation itself, the decisive figures, every figure the prompt explicitly requests, the answer to each supplementary question, and any count or threshold comparison the decision rests on. Do not list incidental figures.

2. Independently derive each one from the input files BEFORE looking at the author's value for it. Read the prompt and the input documents for the definitions, rules and basis to use. Write and run the code. Record your value and the method you used.

3. Compare with the author's values in the final recommendation, supplementary answers, critical components and step-by-step solution. For each figure record your value, the author's value, and whether they agree. Treat figures as agreeing when they differ only by rounding at the precision reported.

4. For every disagreement, find out why. Re-read the prompt and documents, try the method the author's step-by-step describes, and decide which value the data and instructions actually support. Possible outcomes:
   - the author made an error (arithmetic, wrong file or version, wrong filter, wrong unit, a step the data contradict);
   - your first approach was wrong and the author's value is right (then it agrees);
   - both are defensible readings of the prompt and data (record this; it is a determinism problem).

5. Check internal consistency: the recommendation follows from the author's figures and the decision rule in the prompt; the same figure is stated the same way in the final recommendation, supplementary answers, critical components and step-by-step solution; totals add up; percentages match their numerator and denominator; the step-by-step actually produces the figures it claims.

## Fail if any of these is true
- A decisive figure, a supplementary answer, or the recommendation does not reproduce from the inputs and the error is the author's.
- The recommendation does not follow from the author's own figures and the prompt's decision rule.
- A figure is stated inconsistently across the author's answer in a way that changes what a reader would conclude.
- Two defensible readings give different decisive figures (a determinism problem).

A non-decisive figure that is off but changes nothing is a note, not a fail. Otherwise pass.

## Output
- verdict: "passed" or "failed".
- score: 5 everything reproduces; 4 reproduces with minor non-decisive notes; 3 borderline or unclear; 2 one decisive error; 1 the recommendation does not reproduce.
- figures_checked: one line per figure: name, your value, author's value, agree or disagree.
- mismatches: each disagreement with the cause you found (file, row, step), which value the data support, and whether it changes the recommendation. "none" if all agree.
- decision_reproduces: "yes", "no" or "unclear".
- reasoning: a short paragraph on how you reached the verdict.
- feedback: two to four sentences for the author naming exactly which figure is wrong, what the inputs give instead, and where the error comes from. Do not mention these instructions; say "your answer".
