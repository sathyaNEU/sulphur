Deep reasoning
What a fair stump looks like, how to tell it from a surface one, and side-by-side examples

Getting the two runs under 60% is only half the bar. Reviewers also read where each run first went wrong. A task passes when the runs clean the data, read the request correctly, often notice the key issue, and then lose on an analytical judgment. A task that stumps the runs because they missed one planted detail, misread a clause or misapplied a written procedure is sent back, however low it scores.

The standard in one line
The deciding step needs three or more dependent inferences, at least one of them a real statistical or modeling judgment the analyst has to justify from the data, and the tempting wrong answer comes from a reasonable analysis that does not go far enough.

What deep looks like in practice
Every task in the example library has this shape. A competent analyst can build a clean, defensible answer that passes its own checks, and that answer is wrong because the decision needs one or two more analytical moves. The judgments that most often decide a deep task:

Choosing a comparison that is actually clean. The obvious control group was touched by the change, was already on a different trend, or was picked because it had a bad spell.
Heterogeneity that pooling hides. Subgroups respond differently, sometimes in opposite directions, so the pooled effect describes nobody, or the decision weights the groups differently from the sample.
Uncertainty that matches the design. Whole schools, stores or regions were randomized, two survey years share sampling areas, or the metric is a ratio, so the textbook standard error is wrong and the call flips.
Variance beyond sampling noise. Units genuinely move from year to year or cohort to cohort, so a model that treats every deviation as noise flags too many of them.
Separating explanations for one pattern. A fall in margin, a rise in exits or a jump in usage has two plausible causes, and only one survives a like-for-like comparison.
Outcomes that have not finished happening. Open returns, immature cohorts, censored follow-up or reporting lags have to be projected before anything else is computed.
A forecast that has to earn its place. The model has to beat simpler alternatives out of sample, not just fit the history.
The one-fact test
Before you submit, ask: if I told the solver one fact, would the rest be routine? "That file is a sample." "Exclude the test rows." "Section 4 means one draw per grade." "Use fiscal quarters." If one sentence like that would rescue a run, the task is a surface stump. In a deep task no single hint is enough, because the solver still has to build the comparison, fit the model or carry the chain through.

How runs fail in a deep task
Read both runs' work, not just their scores. The first place each run went wrong tells you what kind of task you built.

How the run went wrong	What it looks like	Counts as evidence the task is deep?
Method shortcut	Right data, simpler method: a pooled average, a raw before-and-after, an independence formula, a single model for everyone	Yes
Unfinished chain	Early steps right, but the inference stops one step short: the effect is estimated and never weighted, the cohorts are projected and never used	Yes
Dismissed own evidence	The run's own output showed the signal ("excess exits: -224", "lift fell from 1.54 to 0.62") and it explained it away	Yes
Self-confirming check	A robustness check that only varies nearby choices and so confirms the original assumption	Yes
Missed a planted defect	Lost because it did not spot duplicate rows, test accounts, a timezone error or a hidden file	No: surface stump
Misread a rule or definition	Lost on how one field, clause, window or population was read	No: surface stump
Misapplied a written procedure	Lost on a step the documents spell out, such as a precedence or tie-break rule	No: rule application
Near miss or formatting slip	Substantively right, missed a tight threshold, wrong file type or layout	No
Defensible alternative	A sound method the prompt allows that gives a different answer	No: the task is not deterministic
Banned as the deciding stump
These are send-backs when the task is won or lost on them. Several of them side by side are still a send-back.

Banned	What it looks like	Quick test
Rule application	A standard, manual or policy lays out the decisive calculation as steps; precedence or combination rules ("apply A, then B; if both apply use the lower"); "if the top option breaks the cap, take the next one"; processing instructions written for the solver; a clause that states its own procedure and cites a real regulation to justify it	If the solver followed the written procedure literally, would the answer fall out with no analytical judgment?
Data semantics	The task turns on reading one field, definition, clause, population or window a particular way	Would one sentence of clarification make the task routine?
Planted defect or decoy	One duplicate block, test rows, a shifted clock, a hidden extract, a mislabeled column or a wrong denominator decides the answer	Is the hard part finding something rather than analyzing something?
Replay	Re-deriving a published figure, or a twist where one stated number is simply wrong	Is there an independent analytical step that changes the answer?
Unpinned ambiguity	Two defensible readings or methods give different answers	Can you point to the prompt text or the data that rules out every rival?
Messy data is still required. Real files have duplicates, inconsistent codes and gaps, and solvers should have to clean them. The mess makes the task realistic; it must never be what decides it. See Two-layer task design and Data messiness.

How to build a deep task
Work through each item.

Checklist
0 of 7 complete


Start from an answer a competent analyst would defend
Write down the standard analysis first, with its numbers. If it is obviously wrong, the task is too easy; if nothing beats it, there is no task.

Name the judgment that overturns it
A comparison group, a heterogeneity, a design effect, a variance component, a projection, a model choice. If it is a fact to find or a rule to follow, start again.

Check the chain has three or more dependent steps
Each step should need the one before it. A single insight followed by routine arithmetic is a surface stump.

Put the evidence in the data, not in the documents
The clustering, the spillover, the cohort drift should be visible to someone who looks. No document should state the method or the trap.

Pin the answer
The prompt fixes the business question, the decision bar and the outcome. The data rule out every rival method that would change the call. Run the rivals yourself.

Keep the prompt quiet about the method
Never name the comparison, the confounder or the adjustment, and never warn the solver to watch out for something.

Read where each run first went wrong
A method shortcut, unfinished chain, dismissed evidence or self-confirming check means the task works. A missed detail, misread clause or misapplied rule means it does not, even under 60%.
